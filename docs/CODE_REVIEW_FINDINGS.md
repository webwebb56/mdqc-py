# Python Port Code Review Findings

This file captures the implementation review findings raised after the initial Python port build. These should be resolved before the first Windows release candidate.

## 1. Service never starts the watcher

**Location:** `src/mdqc/service/lifecycle.py:444-446`
**Priority:** P0

`main_async()` starts the finalizer, uploader, and prune loops, but no `WatchdogObserver` is ever constructed or started. In the shipped service path, dropping a raw file into a configured watch directory will not call `finalizer.observe()`, so the core data path never begins. The smoke test builds its own observer/pump and therefore does not cover this service entry point.

**Recommended fix:**

In `_build_state()` or `main_async()`, construct a `WatchdogObserver` from `cfg.instruments` and bridge its thread callback into the asyncio loop with `loop.call_soon_threadsafe`. Start it after the API server is live and stop it during shutdown.

Add an integration test that boots `main_async()` with a configured watch directory, drops a fake raw file, and verifies the service-owned observer reaches the finalizer. Do not rely only on the manually assembled smoke pipeline.

## 2. Ready files are only logged

**Location:** `src/mdqc/service/lifecycle.py:324-331`
**Priority:** P0

The service's processed callback only logs `file_ready`; it does not classify the run, run Skyline, enqueue the payload, record activity or failures, or mark the finalizer done/failed. Even manual `/api/reprocess` requests will leave files in `PROCESSING` until timeout and produce no payload.

**Recommended fix:**

Replace `_processed_callback()` with the real processing path:

- find the matching instrument config;
- classify the path;
- skip non-QC samples and mark them done;
- resolve the configured template path;
- run the extractor;
- enqueue successful extraction results to spool;
- record activity and failed-files entries;
- publish tray/web events;
- call `finalizer.mark_done()` or `finalizer.mark_failed()`.

Add a service-level integration test that uses a fake extractor injected into `AppState`, then verifies a dropped file lands in `spool/completed` in local-only mode.

## 3. Payload schema is not Rust-compatible

**Location:** `src/mdqc/spool/store.py:126-158`
**Priority:** P1

The emitted payload uses `schema_version = "1.0"` plus fields such as `run.raw_file_path` and `extraction.template_path`. The Rust/cloud contract uses schema `1.1` and expects fields like `run.raw_file_name`, `vendor`, `acquisition_time`, `extraction.template_name`, and optional method/column fields. This violates the migration requirement that Rust and Python payloads remain compatible.

**Recommended fix:**

Port the Rust `QcPayload`, `RunInfo`, and `ExtractionInfo` shape exactly:

- set `schema_version` to `1.1`;
- emit `run.raw_file_name`, not `raw_file_path`;
- include `run.vendor`, `acquisition_time`, `method_name`, and `column_info`;
- emit `extraction.template_name`, not `template_path`;
- keep `baseline_context` and `comparison_metrics` as nullable fields;
- verify enum casing matches Rust serialization.

Add a golden payload fixture generated by the Rust agent and assert Python output matches the same field names and types.

## 4. Web auth ignores the cookie it creates

**Location:** `src/mdqc/service/lifecycle.py:157-160`
**Priority:** P1

The base template stores the launch token in `mdqc_session` and removes it from the URL, but the FastAPI middleware only accepts the IPC header or `?token=` query parameter. After the first authenticated page load, normal links and HTMX posts will no longer include the query token and will return `401`.

**Recommended fix:**

Update the middleware and `_check_token()` to accept `request.cookies["mdqc_session"]` as an authentication source, alongside the header and query parameter.

Add tests for:

- first load with `?token=...`;
- second navigation authenticated only by cookie;
- HTMX-style POST authenticated only by cookie;
- invalid cookie still returns `401`.

## 5. CI can publish an installer with empty NSSM

**Location:** `.github/workflows/ci.yml:77-83`
**Priority:** P1

When `installer/nssm.exe` is missing, CI creates an empty placeholder and continues to build/upload the installer. That release artifact will install a zero-byte `nssm.exe`, so service registration/start will fail on customer machines.

**Recommended fix:**

Make the installer job fail unless a real, SHA-256-verified `installer/nssm.exe` is present. Preferred approaches:

- commit a vetted `nssm.exe` and document its checksum; or
- fetch NSSM in CI from a pinned URL and verify the expected SHA-256 before packaging.

Remove the placeholder creation step. Add a packaging preflight in `scripts/package.py` that rejects zero-byte or checksum-mismatched NSSM binaries.

## 6. Failed retry is blocked by the processed registry

**Location:** `src/mdqc/watcher/finalizer.py:124-132`
**Priority:** P2

`mark_failed()` adds the raw path to `ProcessedRegistry`, and `observe()` refuses any path already in that registry. As a result, `/api/failed/retry` and scan-based retry cannot re-enqueue failed files.

**Recommended fix:**

Only successful `mark_done()` should add a path to the processed registry. For failures, remove the tracker but leave the path eligible for explicit retry.

If automatic scan retry must remain blocked, add a separate failed-path suppression mechanism and make `/api/failed/retry` call `observe(..., force=True)` or remove the failed path from that suppression set before re-enqueueing.

Add tests that:

- `mark_failed()` does not add to `ProcessedRegistry`;
- `failed retry <path>` re-observes a failed file;
- `failed retry all` re-enqueues all retryable failed files.
